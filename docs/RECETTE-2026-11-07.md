- **Application** : plateforme web de réservation de salons de beauté (Tunisie), Next.js 16 + MongoDB, PWA. Rôles : visiteur, cliente, employée, gérante, Super Admin. Langues FR / AR / EN.
- **Environnement isolé** : base dédiée `beautyhub_qa_nov`, remplie par le seed (69 utilisateurs, 12 salons, ≈ 1 000 réservations, 38 avis). Les bases `beautyhub` (démo de l'équipe) et `beautyhub_test` n'ont pas été modifiées. Pour simuler des rendez-vous déjà passés, l'heure de quelques réservations de test a été reculée directement dans cette base isolée.
- **Comptes** : comptes du seed (`sarra@`, `yasmine@`, `nour@`, `admin@beautyhub.tn`, gérants d'autres salons) + **≈ 110 clientes créées** pendant la campagne.
- **Outils** : scripts Node (sessions Auth.js réelles, une par rôle) ; Chrome headless piloté par le protocole DevTools (navigation, molette, clavier, captures) ; navigateur intégré pour les parcours visibles ; contrôles directs en base.
- **Hypothèses** : public cible = clientes tunisiennes majoritairement sur téléphone ; une mise en production est envisagée après le projet (d'où la sévérité « critique » de QA2-01). Les fonctions simulées par conception (SMS, paiement en mode test, e-mails sans SMTP) sont testées comme telles.

- **Isolation entre salons étanche** : un gérant d'un autre salon (même plan Premium) ne peut ni lire ni modifier les stocks, promotions, employés, blocages d'agenda, notes clientes, encaissements ou factures d'un autre salon (404/403). Basculer vers un salon non possédé → 403.

## 5. Anomalies

Gravité : **Critique** (faille exploitable ou perte de contrôle) · **Majeure** (règle métier fausse, données ou argent touchés, fonction annoncée absente) · **Moyenne** (comportement trompeur ou risqué) · **Mineure** (confort, cohérence).

### Critique

#### QA2-01 — La connexion démo donne un accès Super Admin sans mot de passe
- **Étapes** : `GET /api/auth/csrf`, puis `POST /api/auth/callback/demo` avec `role=ADMIN` (aucun identifiant) ; puis `GET /api/admin/overview`.
- **Obtenu** : **200**, session Super Admin ouverte, sur le **build de production**. Le fournisseur `demo` est listé publiquement par `/api/auth/providers`, les boutons démo s'affichent sur `/connexion` et le pied de page contient « Démo : Espace client · Dashboard salon · Super Admin ». Il suffit que `DEMO_LOGIN=true` (valeur actuelle du `.env`) parte en production.
- **Attendu** : jamais d'accès admin sans authentification hors démonstration locale.
- **Correction proposée** : dans `src/auth.ts:41`, refuser le fournisseur démo quand `NODE_ENV === "production"` sauf variable explicite (ex. `ALLOW_DEMO_IN_PRODUCTION`), et masquer la rubrique « Démo » du pied de page dans ce cas ; ne jamais proposer le rôle ADMIN en démo publique.

### Majeures

#### QA2-02 — Une date impossible fait planter l'API (500)
- **Étapes** : `POST /api/bookings` avec `"date": "2026-13-45"` ; idem `GET /api/salons/:slug/availability?date=2026-13-45` et `GET /api/dashboard/agenda?date=2026-13-45`.
- **Obtenu** : **500 INTERNAL** sur les trois routes. (« 2026-02-30 » renvoie en plus un message faux : « Ce créneau est déjà passé ».)
- **Attendu** : 400 `VALIDATION`.
- **Cause** : le schéma `DATE` ne vérifie que le format `\d{4}-\d{2}-\d{2}` (`src/modules/booking/application/schemas.ts:3`, même motif dans `dashboard/application/schemas.ts:4` et `promotions/application/schemas.ts:4`). **Correction** : `z.iso.date()` (déjà utilisé pour `birthDate`) ou un `refine` de date réelle, dans un schéma partagé.

#### QA2-03 — Réservation acceptée à une heure hors grille (11:07)
- **Étapes** : `POST /api/bookings` avec `"time": "11:07"` (créneaux de 30 min).
- **Obtenu** : **201** ; l'agenda affiche « 11:07 – 11:52 » (capture `01`). Le RDV chevauche 11:00 **et** 11:30 : deux créneaux perdus pour 45 min de prestation. Même chose possible au report.
- **Attendu** : seules les heures proposées par `/availability` sont acceptées.
- **Correction** : dans `createBooking` et `rescheduleBooking`, refuser les minutes non multiples de 30 (ou vérifier que l'heure figure dans les créneaux calculés).

#### QA2-04 — Une cliente peut avoir deux rendez-vous à la même heure
- **Étapes** : réserver lundi 11:00 au Salon Yasmine, puis lundi 11:00 avec une autre professionnelle du même salon, puis lundi 11:00 à Maison Elyssa.
- **Obtenu** : les **3 réservations acceptées** (201).
- **Attendu** : `409` « Vous avez déjà un rendez-vous à cette heure ».
- **Impact** : absences garanties, créneaux bloqués chez plusieurs salons.
- **Correction** : contrôle de chevauchement sur les réservations actives du `clientId` dans `createBooking`.

#### QA2-05 — La cliente peut annuler après l'heure du rendez-vous
- **Étapes** : RDV confirmé dont l'heure est passée depuis 2 h ; la cliente envoie `{ action: "cancel" }`.
- **Obtenu** : **200**, RDV annulé (comptabilisé en annulation tardive). La cliente transforme une absence en simple annulation tardive, et le salon ne peut plus la marquer absente.
- **Attendu** : `409 TOO_LATE` une fois l'heure passée.
- **Correction** : `cancelBooking` (`src/modules/booking/application/use-cases.ts:111`) : si `byClient && booking.startsAt <= now` → refus. `isWithinCancellationWindow` renvoie vrai pour une heure passée (différence négative), ce qui masque le cas.

#### QA2-06 — L'avis d'une cliente absente reste publié
- **Étapes** : RDV confirmé, heure passée ; la cliente publie « Service nul, jamais je ne reviendrai ici. » (1★, accepté dès l'heure du RDV) ; la gérante la marque **absente**.
- **Obtenu** : l'avis 1★ reste sur la fiche publique du salon et compte dans la note.
- **Attendu** : un avis « vérifié » n'existe que pour une visite réelle : masqué ou supprimé quand le RDV passe en absence (et points d'avis repris).
- **Correction** : abonné à `booking.noShow` qui masque l'avis lié et recalcule la note (`refreshSalonRating`).

#### QA2-07 — Aucune limitation de débit (inscriptions, réservations, IA)
- **Étapes et résultats** :
  - 30 inscriptions envoyées en rafale → **30 comptes créés**, aucun 429 ;
  - un compte créé à l'instant, e-mail **non vérifié** → **8 demandes** de RDV acceptées le même jour dans le même salon ;
  - 12 messages simultanés à l'assistante, sans être connecté → **12 réponses 200**, aucun 429.
- **Impact** : un script peut remplir l'agenda d'un salon de demandes fantômes (le créneau est gardé pendant l'attente) ; l'assistante utilise un quota Groq gratuit partagé (8 000 jetons/min, soit 1 à 2 messages/min) : quelques requêtes suffisent à le vider pour tous les utilisateurs, qui basculent alors sur le modèle de secours ou les règles sans IA.
- **Correction** : limitation par IP et par compte sur `/api/auth/register`, `/api/bookings` (POST) et `/api/ai/chat` ; plafond de demandes en attente par cliente (ex. 2), plus strict tant que l'e-mail n'est pas vérifié.

#### QA2-08 — « Ajouter au calendrier » ne fait rien
- **Étapes** : écran « Demande envoyée » → « Ajouter au calendrier ».
- **Obtenu** : toast « Ajouté à votre calendrier », **aucun fichier `.ics` ni lien** (`src/components/booking/booking-flow.tsx:299` : `onClick={() => toast.success(...)}`).
- **Attendu** : ajout réel ou bouton absent. Un retour de succès mensonger est pire qu'une fonction manquante.
- **Correction** : générer un `.ics` (Blob, téléchargement) ou un lien Google Agenda avec date, durée, adresse.

#### QA2-09 — Chiffres d'accueil fictifs présentés comme réels
- **Constat** : l'accueil affiche « **1 342 salons vérifiés** en Tunisie », « Avis vérifiés **96 000** », « Note moyenne **4,8/5** » et une carte « Salon Yasmine **4,9** » (capture `04`) ; même « 1 342 » sur `/pro` et sur la page de connexion.
- **Réalité en base** : 12 salons (8 visibles), 38 avis ; Salon Yasmine noté 4,2 au seed.
- **Cause** : valeurs en dur (`src/app/(site)/page.tsx:150,163-165`, `src/app/(site)/pro/page.tsx:62`, `src/components/auth/auth-stage.tsx:130`).
- **Impact** : promesse publicitaire fausse, perte de confiance dès que la cliente compte les résultats (« 8 salons » sur `/salons`) ; risque juridique si mis en ligne.
- **Correction** : calculer ces chiffres en base (cache de quelques minutes) ou les retirer.

#### QA2-10 — Changer de mot de passe ne déconnecte pas les autres sessions
- **Étapes** : ouvrir deux sessions sur le même compte ; changer le mot de passe dans la première ; `GET /api/me` dans la seconde.
- **Obtenu** : **200** : la seconde session reste valide (jeton JWT de 30 jours).
- **Attendu** : les autres sessions sont fermées (usage n° 1 du changement de mot de passe après un vol de compte).
- **Correction** : champ `passwordChangedAt` (ou version de jeton) inscrit dans le JWT et vérifié au même endroit que le blocage de compte, qui coupe déjà les sessions immédiatement.

#### QA2-11 — Barre de recherche sans indicateur de focus clavier
- **Constat** : les 3 champs (Prestation, Ville, Quand) ont `focus:outline-none` sans remplacement : au clavier, seul le curseur clignotant indique où l'on est (capture `03`). Critère WCAG 2.4.7.
- **Fichiers** : `src/components/site/search-bar.tsx:63, 80, 110`.
- **Correction** : reprendre le motif de l'assistante (`chatbot-widget.tsx:382`) : `focus-within:ring-2 focus-within:ring-ring/60` sur chaque bloc.

## 6. Synthèse UI / UX

**Points forts**
- Identité visuelle cohérente (prune sur ivoire, arches, typographie Plus Jakarta Sans / IBM Plex Sans Arabic), hiérarchie claire, 1 seul `h1` par page, aucun saut de niveau de titre.
- Tunnel de réservation lisible : étapes numérotées, récapitulatif permanent, points affichés avant de réserver, textes honnêtes sur le créneau non bloqué.
- Arabe réellement miroir (navigation, cartes, chiffres latins), même contenu qu'en français.
- Téléphone : même contenu que sur ordinateur, rangées défilantes, barre « Réserver » fixe ; aucune page ne déborde à 375 px.
- Accessibilité de base : lien d'évitement, boutons et images nommés (0 élément sans nom sur 186 pages), contraste conforme sur les textes vérifiés (6,12:1 pour le texte secondaire).

**Frictions principales**
1. **Retours trompeurs** : calendrier factice (QA2-08), +20 pts (QA2-16), chiffres d'accueil (QA2-09). Ils minent la promesse « en toute confiance » du slogan.
2. **Actions sensibles en icônes seules** côté salon (QA2-13) et aucune action sur un RDV confirmé (QA2-14).
3. **Boutons désactivés muets** (QA2-22) : la cliente ne comprend pas pourquoi elle ne peut pas confirmer.
4. **Clavier** : focus invisible dans la recherche (QA2-11).
5. **Cas d'erreur négligés** : 404 en anglais et en noir (QA2-15), dates brutes (QA2-21).
